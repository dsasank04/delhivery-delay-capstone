# Delivery Delay Intelligence — Capstone

An end-to-end machine-learning project that predicts last-mile parcel delays across a 24-hub Indian logistics network and turns the predictions into an operations action list.

The project covers the full workflow:

1. **Clean** a messy raw shipment export and run exploratory analysis.
2. **Regress** delivery hours.
3. **Classify** shipments as delayed or on time, and tune an alert threshold.
4. **Segment** hubs into operating playbooks with K-Means.
5. **Package** the classifier and **score** a batch of new parcels.

> **Note:** All data is synthetic. It is generated by `generate_data.py` with fixed random seeds, so every number below can be reproduced exactly.

## Getting started

### Requirements

- Python 3.10 or later
- Packages listed in `requirements.txt` (pandas, numpy, scikit-learn, joblib)

### Setup

```bash
python -m venv .venv

# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

pip install -r requirements.txt
```

### Run the pipeline

Run every script from the repository root, in this order:

```bash
python generate_data.py          # optional: data/ already contains the generated files
python part_a_clean_eda.py       # writes data/modelling_table.csv + outputs/part_a_*
python part_b_regression.py      # outputs/part_b_*
python part_c_classification.py  # outputs/part_c_*
python part_d_segments.py        # outputs/hub_*, segment_profile, tier_vs_segment_mismatch
python package_model.py          # models/* + outputs/part_d_reload_check.csv
python predict_delay.py          # outputs/new_shipment_actions.csv
```

Parts B, C and D each depend only on Part A. `package_model.py` needs Part C's output. `predict_delay.py` needs both `package_model.py` and Part D.

## The data

Each shipment has these fields:

| Field | Description |
|---|---|
| `hub_id` | Origin hub (joined to `hubs.csv` for city, region, tier, capacity) |
| `service_type` | Express / Standard / Economy |
| `payment_mode` | Prepaid / COD |
| `parcel_weight_kg`, `distance_km`, `declared_value`, `n_stops` | Parcel and route attributes |
| `rain_flag`, `sale_event_flag` | Weather and sale-period indicators |
| `dispatch_time` | Dispatch timestamp (Jul–Sep 2026) |
| `label_print_batch`, `scanner_build_no`, `tape_roll_no`, `sticker_serial_mod`, `shelf_slot_no` | **Noise columns.** They have no real relationship to delay and are included to test feature selection. |
| `delivery_hours` | Target: actual hours to deliver (historical data only) |

A shipment is **delayed** when `delivery_hours` is greater than the promised time for its service:

| Service | Promised hours |
|---|---|
| Express | 36 |
| Standard | 60 |
| Economy | 96 |

The raw export contains the kinds of problems a real export has: duplicate rows, inconsistent `service_type` spellings, missing values, rupee-formatted text values (`"₹1,290"`), and a 999 kg scanner-fault sentinel.

## Part A — Cleaning and EDA

`src/shipment_prep.py` holds the shared cleaning logic, so training and scoring always use the same steps.

**`clean_shipments(raw, medians=None)`**

1. Drops exact duplicate rows (24 removed, leaving 1,200).
2. Normalises `service_type` (12 spellings become 3).
3. Fills missing `payment_mode` with `"Unknown"`.
4. Parses `declared_value` into a numeric `declared_value_inr`.
5. Parses `dispatch_time` into a datetime.
6. Treats weights above 100 kg as missing (5 sentinel rows).
7. Fills missing distance, weight and value with medians. The medians are computed from the training data, or passed in when scoring.

**`build_features(clean, hubs)`** joins the hub attributes and derives `promised_hours`, `is_cod`, `is_weekend`, `dispatch_hour` and `log_declared_value`. It never uses the target.

**Key findings** (`outputs/part_a_delay_by_group.csv`):

| Group | Delay rate |
|---|---|
| Express | 49.0% |
| Standard | 20.6% |
| Economy | 8.6% |
| Tier 1 hubs | 4.0% |
| Tier 2 hubs | 21.5% |
| Tier 3 hubs | 44.0% |
| Distance 0–200 km | 2.2% |
| Distance 601+ km | 85.2% |

The overall delay rate is 23.2% (278 of 1,200 shipments).

## Part B — Delivery-hours regression

- 70 / 15 / 15 train / validation / test split (840 / 180 / 180 rows).
- The scaler is fitted on the training rows only.
- Compares a mean baseline, Linear Regression, a depth-tuned Decision Tree, a Random Forest and Gradient Boosting.
- Includes a tree-depth diagnostic, a Gradient Boosting learning-rate experiment and 5-fold cross-validation of the top two models.

| Model | Val RMSE | Val R² |
|---|---|---|
| Mean baseline | 18.86 | −0.02 |
| **Linear Regression** | **4.89** | **0.931** |
| Gradient Boosting | 4.92 | 0.931 |
| Random Forest | 5.51 | 0.913 |
| Decision Tree (depth 6) | 6.28 | 0.887 |

The final model, **Linear Regression**, scores **RMSE 4.52 h and R² 0.949** on the test set.

## Part C — Delay classification

- Stratified 70 / 15 / 15 split.
- Compares an "all on time" baseline, Logistic Regression, a depth-tuned Decision Tree and a Random Forest. Metrics come from the confusion matrix.
- **Feature signal:** the ANOVA F-test and Random Forest importances both rank the five noise columns near the bottom. In a SelectKBest sweep, **k = 7** gives the best validation F1 (0.833).
- **Tuning:** compares GridSearchCV (27 candidates × 5 folds), RandomizedSearchCV (9 × 5) and a default forest, all on the 7 selected features. The default forest has the best validation F1.
- **Alert threshold:** the highest probability threshold whose validation recall is at least 0.80. The result is **0.5**.

**Final configuration:** SelectKBest(k=7) + RandomForest (100 trees, unlimited depth, min_samples_leaf = 1).

Results on the test set at threshold 0.5:

| Accuracy | Precision | Recall | F1 |
|---|---|---|---|
| 0.867 | 0.689 | 0.756 | 0.721 |

## Part D — Hub segmentation

- Builds a per-hub profile with mean delivery hours, delay rate, mean distance and mean stops.
- Scales the profile and clusters it with **K-Means (K = 3)**.
- For separation evidence, computes the ratio of mean across-cluster distance to mean within-cluster distance for K = 2 to 5.
- Names the clusters by delay rate:

| Segment | Hubs | Delay rate | Mean distance (km) |
|---|---|---|---|
| Standard | 7 | 2.6% | 189 |
| Watch | 8 | 15.5% | 314 |
| Escalate | 9 | 46.0% | 470 |

**Tier vs segment:** four hubs perform differently from what their official tier label suggests. Planning by tier alone would misclassify them.

| Hub | City | Official tier | Behaves like |
|---|---|---|---|
| HUB07 | Kolkata | 1 | Watch |
| HUB13 | Nagpur | 2 | Escalate |
| HUB15 | Kochi | 2 | Escalate |
| HUB22 | Dehradun | 3 | Watch |

## Packaging and scoring new parcels

`package_model.py` refits the final Part C pipeline and saves these files to `models/`:

- the pickled model
- the alert threshold
- the feature order
- the imputation medians

It then reloads the pickle and checks that it reproduces the same probabilities (max diff = 0.0).

`predict_delay.py` cleans `data/new_shipments.csv` with the **stored historical medians**, scores each parcel, and assigns an action:

| Condition | Action |
|---|---|
| Probability below threshold | No action |
| Flagged, at an Escalate hub | Escalate to hub manager |
| Flagged, at any other hub | Proactive customer call |

Of the 48 new parcels, **8 are flagged**: 6 escalated to a hub manager and 2 for a proactive customer call. The full list is in `outputs/new_shipment_actions.csv`.

## Design notes

- **No leakage:** scalers, feature selectors and imputation values are fitted on training data only. The test set is evaluated once per part.
- **Reproducibility:** every split, model and search uses `random_state=42`. Data generation uses fixed seeds.
- **Shared preprocessing:** training and inference both call the same `clean_shipments` and `build_features` functions, so the two cannot drift apart.
